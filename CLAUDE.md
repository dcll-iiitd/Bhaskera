# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Bhaskera — Ray-native distributed LLM training and inference framework (Python ≥ 3.11, package under `src/bhaskera`, version 2.2.0). Wraps PyTorch FSDP2/DDP, HF `transformers`, PEFT LoRA/QLoRA, and a persistent Ray Data tokenisation cache behind a YAML-driven CLI. Supports SFT and continual pre-training (CPT) of dense and MoE causal LMs on single-node and multi-node SLURM.

`ARCHITECTURE.md` (~1060 lines) is the authoritative design reference — read the relevant section before non-trivial changes. Sub-packages carry their own `README.md`. Note that ARCHITECTURE.md occasionally drifts from code (e.g. §4.9 says the `Evaluator` is constructed in `worker_fn`; it is actually built inside `trainer.train`, `trainer/loop.py:136`) — trust the code when they disagree.

## Commands

```bash
bash setup.sh                       # CUDA probe → uv venv → matched torch wheel → flash-attn out-of-band
                                    # BHASKERA_CUDA=12.4 / BHASKERA_VENV=/path to override
source bhaskera-activate.sh         # generated by setup.sh — CUDA + venv in one line
pip install -e ".[dev,mlflow,wandb]"
pip install bitsandbytes            # only for model.quantization: qlora (GPU-specific, not in pyproject)
```

Tests — pytest; the inference suite is the only test coverage in the repo, and needs no GPU or real model:

```bash
pytest src/bhaskera/inference/tests/test_inference.py -v
pytest src/bhaskera/inference/tests/test_inference.py::TestLloydMaxCodebook -v   # one class
pytest src/bhaskera/inference/tests/test_inference.py -k round_trip -v           # one test
```

Nothing covers config, introspect, data, distributed, trainer, evaluation, or plugins — changes there are validated only by running a job.

Lint: `ruff check src/` (line-length 100, `[tool.ruff]` in `pyproject.toml`).

Run (console scripts from `[project.scripts]`):

```bash
bhaskera-tokenize --config configs/tokenize.yaml --split both   # prints the tokenized_path: to paste into the train config
bhaskera-train    --config configs/qwen.yaml --num-workers 4
bhaskera-infer    --config configs/inference_param2.yaml --prompt "..."
bhaskera-diag     --num-workers 4                               # NCCL all-reduce + bandwidth check
bhaskera-dashboard                                              # MLflow UI on the login node
sbatch scripts/submit.sh --config configs/2node.yaml            # SLURM (ray symmetric-run, Ray >= 2.49)
```

Training is two-phase by design: tokenise once, paste the printed path into `data.tokenized_path` (and `val_tokenized_path`), then train. There is **no** eval console script — evaluation runs in-training via `evaluation.enabled: true`.

`configs/` doubles as the scenario catalogue: `2node.yaml` (MoE + FSDP, 2×2 GPUs), `param_qlora.yaml` (QLoRA + DDP), `qwen_ddp.yaml` / `qwen_hybrid_shard.yaml` (dense variants), `fsdp_cpt.yaml` / `pre.yaml` (CPT), `eval.yaml` (validation + benchmarks), `adadelta.yaml` / `lion.yaml` (optimizer backends), `cpt_token.yaml` / `tokenize*.yaml` (tokenisation jobs).

## Architecture

**Control flow.** `bhaskera-train` (driver, head node) → `load_plugins(cfg)` → parse YAML into the `Config` dataclass tree → `ray.init()` → build a lazy tokenized `ray.data.Dataset` → `TorchTrainer(train_loop_config=cfg.as_dict()).fit()`. Ray Train spawns one worker per GPU running `launcher/worker.py:worker_fn`: `Config.from_dict` → `load_plugins` again → get train (and optionally `"val"`) dataset shards → `build_model` → `wrap_model` → `build_logger` → `trainer.train`. Ray is off the hot path once training starts; a step is bounded by NCCL only.

**`introspect.py` is the keystone.** One structural pass over the loaded model yields a `ModelProfile` (decoder layer class, expert modules, router names, LoRA targets, aux-loss support, dtype). Every architecture-dependent decision downstream consumes it — the codebase has **zero hardcoded model names**, and a new architecture normally needs no code change. If a layout is genuinely novel, extend `_LAYER_CONTAINER_ATTRS` / `_EXPERT_LEAF_NAMES` in `introspect.py`; never special-case in trainer, wrap, LoRA, or checkpoint code.

**Registries are the extension mechanism** — extend by adding files, not editing core code. They differ in how registration fires, which is the part that bites:

| Registry | Decorator | How it gets loaded |
|---|---|---|
| Dataset | `@register` / `@register_raw` | Must add an import to `data/datasets/__init__.py` or the decorator never fires |
| Chat format | `@register_format` | Lazily via `_ensure_builtins_loaded` (kept lazy so Ray doesn't pickle HF) |
| Optimizer | `@register_optimizer` | Module path declared in `plugins.optimizers:` YAML; `load_plugins` runs in **both** driver and worker |
| Metric / Benchmark | `@register_metric` / `@register_benchmark` | Lazy-imported on demand by `get_metric` / `get_benchmark` — no declaration needed |
| Model loader | `@register_model` | Any module imported before `build_model` |

**Subsystem contracts:**
- `config.py` — `_dict_to_config` constructs each leaf explicitly rather than `**unpack`, so unknown YAML keys are ignored while the tree shape stays invariant (`cfg.training.distributed.fsdp.x` can never `AttributeError`). `as_dict()`/`from_dict()` must round-trip — Ray Train serialises the config to every worker.
- `models/` — `build_model(cfg, device) -> (model, profile)`. Order is load-bearing: quantization config → load → introspect → Liger → LoRA → (later) FSDP wrap.
- `distributed/` — `wrap_model(model, cfg, local_rank, profile)`; FSDP is `fully_shard(expert) → fully_shard(layer) → fully_shard(root)`, then AC. DDP applies AC *before* the wrap.
- `trainer/` — no Ray, no SLURM, no distributed init; assumes `torch.distributed` is up and the model is already wrapped, which keeps it usable under raw `torchrun`. `build_optimizer` dispatches on `training.optimizer.backend`: `default` (fused AdamW + 1-D/2-D weight-decay split), `torch` (any `torch.optim` class by `class_name`), `plugin` (`OPTIMIZER_REGISTRY` lookup by `name`).
- `evaluation/` — `Evaluator` facade over `run_distributed_validation` and `run_benchmarks`; per-rank losses are all-reduced, metrics computed on rank 0 and `broadcast_object_list`'d back.
- `utils/loggers/` — `BaseLogger.log(metrics, step)` must never raise into the training loop; `MultiLogger` fans out with W&B/MLflow on rank 0 and the Ray logger on every rank.

**Tokenisation cache** is keyed on `sha256(model_name | seq_len | dataset_name | format | format_options | is_cpt)[:16]` — deliberately not Python `hash()`, which is per-process randomised. Writes go via `<path>.tmp` so a crashed run can't poison the cache. `data.pack_sequences` is an alias for `is_cpt`; both enable N-to-M continuous packing, and the flag participates in the cache key so packed and unpacked caches never collide.

## Invariants that are easy to break

- **Mixed precision under FSDP has exactly one owner.** When `strategy == "fsdp"` the autocast context is `nullcontext()` — FSDP2's `MixedPrecisionPolicy` owns param/reduce/output dtypes. Adding `torch.autocast` on top double-casts and corrupts gradient reduction. Autocast is enabled **only** under DDP.
- **LoRA dtype is strategy-gated.** FSDP2 requires uniform original param dtype in a shard group, so LoRA params are cast to base dtype there. Under DDP/QLoRA they stay fp32 — casting starves AdamW's second moment at typical LoRA LRs (~2e-4, β₂=0.95). See the annotations in `models/lora.py`.
- **QLoRA is DDP-only.** BitsAndBytes `Params4bit` cannot be sharded by `fully_shard`. `build_quantization_config` raises `ValueError` up front rather than letting FSDP fail internally — keep that check ahead of any model work.
- **Grad-sync toggling is what makes accumulation efficient.** `_set_grad_sync` dispatches per wrapper so all-reduce fires once per optimizer step. DDP forces `find_unused_parameters=True` on MoE, which forces `static_graph` off; the effective value is stashed as `_bhaskera_static_graph` for the loop to read.
- **Router detection must stay parent-scoped.** Substring-matching `gate`/`router` finds `gate_proj` in every SwiGLU model and wrongly drops it from LoRA targets. Router search is restricted to modules whose parent is the parent of an experts container.
- **Checkpoints are valid only with the `.complete` sentinel**, written last by rank 0. To skip a suspect checkpoint, delete the sentinel, not the directory. Retention (`keep_last_n`) prunes by ascending `avg_loss`, not by step.
- **Optimizer offload must not double-fire.** `EvaluationLifecycle` and `run_distributed_validation` both offload optimizer state to CPU; the `_bhaskera_offloaded` flag is what keeps that idempotent.
- **NCCL env vars belong in `scripts/submit.sh`, not Python** — Ray Train calls `init_process_group` before user code runs, so setting them in-process is too late.

## Conventions

- Every module opens with `from __future__ import annotations`; docstrings and comments explain *why* (often citing the bug that motivated the code) rather than restating it.
- Heavy imports (`bitsandbytes`, HF, `liger_kernel`, plugin modules) are deferred to call sites so absent optional deps and Ray pickling stay unaffected.
- CLIs use stdlib `argparse` and preserve exit codes.
- ARCHITECTURE.md §7 has copy-pasteable recipes for each extension type; keep it updated when adding a registry or changing a contract.

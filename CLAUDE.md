# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Bhaskera — Ray-native distributed LLM training and inference framework (Python ≥ 3.11, package under `src/bhaskera`, installed as `bhaskera` v2.2.0). Wraps PyTorch FSDP2/DDP, HF `transformers`, PEFT LoRA, and a persistent Ray Data tokenisation cache behind a YAML-driven CLI. Targets SFT of dense and MoE causal LMs on single-node and multi-node SLURM.

`ARCHITECTURE.md` (818 lines) is the authoritative technical reference — read the relevant section before non-trivial changes. Each sub-package also has its own `README.md` documenting per-module behaviour.

## Commands

Setup (one-shot; detects CUDA, creates a `uv` venv, installs the matching torch wheel, then flash-attn out-of-band):

```bash
bash setup.sh                      # BHASKERA_CUDA=12.4 / BHASKERA_VENV=/path to override
source bhaskera-activate.sh        # generated by setup.sh — CUDA + venv in one line
pip install -e ".[dev,mlflow,wandb]"
```

Tests — pytest, currently only the inference suite (no GPU or real model needed):

```bash
pytest src/bhaskera/inference/tests/test_inference.py -v
pytest src/bhaskera/inference/tests/test_inference.py::TestLloydMaxCodebook -v          # one class
pytest src/bhaskera/inference/tests/test_inference.py -k "round_trip" -v                # one test
```

Lint: `ruff check src/` (line-length 100, configured in `pyproject.toml`).

Run:

```bash
bhaskera-tokenize --config configs/tokenize.yaml --split both   # writes parquet cache, prints tokenized_path:
bhaskera-train    --config configs/qwen.yaml --num-workers 4
bhaskera-infer    --config configs/inference_param2.yaml --prompt "..."
bhaskera-diag     --num-workers 4                               # NCCL all-reduce + bandwidth check
bhaskera-dashboard                                              # MLflow UI on the login node
sbatch scripts/submit.sh --config configs/2node.yaml            # SLURM
```

The workflow is two-phase by design: tokenise once, paste the printed path into the training config's `data.tokenized_path` (and `val_tokenized_path`), then train. Live tokenisation works but wastes GPU time.

## Architecture

**Control flow.** `bhaskera-train` (driver, head node) parses YAML → `Config` dataclass tree → `ray.init()` → builds a lazy tokenized `ray.data.Dataset` → `TorchTrainer(train_loop_config=cfg.as_dict()).fit()`. Ray Train spawns one worker process per GPU running `launcher/worker.py:worker_fn`, which does `Config.from_dict(...)` → `build_model` → `introspect_model` → optional Liger + LoRA → `wrap_model` (FSDP2 or DDP) → `trainer.loop.train`. Ray is off the hot path once training starts; a step is governed by NCCL only.

**`introspect.py` is the keystone.** One structural pass over the loaded model produces a `ModelProfile` (decoder layer class, expert modules, router names, LoRA targets, aux-loss support, dtype). Every architecture-dependent decision downstream consumes that profile — the codebase has **zero hardcoded model names**, and new architectures normally require no code change. Supporting an unusual layout means extending `_LAYER_CONTAINER_ATTRS` / `_EXPERT_LEAF_NAMES` in `introspect.py`, never special-casing in the trainer, wrap, LoRA, or checkpoint code.

**Subsystem contracts** (each is consumed by name across modules):
- `config.py` — frozen dataclass tree; `_dict_to_config` constructs each leaf explicitly rather than `**unpack`, so unknown YAML keys are ignored but the tree shape is invariant (`cfg.training.distributed.fsdp.x` never raises `AttributeError`). `as_dict()`/`from_dict()` must round-trip — Ray Train serialises the config to every worker.
- `data/` — two parallel registries: `@register(name)` (tokenized builder, used by training) and `@register_raw(name, text_col=...)` (raw builder, used by `bhaskera-tokenize`). Format renderers are `(row, tokenizer, options) -> str` registered via `@register_format`; imported lazily so Ray doesn't pickle HF at registry-import time. New dataset modules must be imported in `data/datasets/__init__.py` for the decorator to fire.
- `models/` — `build_model(cfg, device) -> (model, profile)`; Liger kernel patching happens **before** LoRA and before FSDP wrap.
- `distributed/` — `wrap_model(model, cfg, local_rank, profile)`; FSDP path is `fully_shard(expert) → fully_shard(layer) → fully_shard(root)` then activation checkpointing; DDP path applies AC pre-wrap.
- `trainer/` — pure loop: grad accumulation, MoE aux loss, throughput/MFU, checkpoint cadence.
- `utils/loggers/` — `BaseLogger.log(metrics, step)` must never raise into the training loop. `build_logger` fans out to a `MultiLogger`; W&B/MLflow on rank 0, Ray logger on every rank.

**Tokenisation cache.** Key is `sha256(model_name | seq_len | dataset_name | format_name | format_options)[:16]` — deliberately not Python `hash()`, which is per-process randomised. Changing `seq_len`/`format`/`format_options` invalidates automatically. Writes go through `<path>.tmp` so a crashed tokenize run can't poison the cache.

## Invariants that are easy to break

- **Mixed precision under FSDP has a single source of truth.** When `strategy == "fsdp"` the autocast context is `nullcontext()` — FSDP2's `MixedPrecisionPolicy` owns param/reduce/output dtypes. Adding `torch.autocast` on top double-casts and corrupts gradient reduction. Autocast is enabled **only** under DDP.
- **LoRA dtype is strategy-gated.** FSDP2 requires uniform param dtype within a shard group, so LoRA params are cast to base dtype; under DDP they stay fp32 because casting starves AdamW's second moment at typical LoRA LRs. This is the subtlest interaction in the codebase — see the comments in `models/lora.py`.
- **Grad-sync toggling is what makes accumulation efficient.** `_set_grad_sync` dispatches per wrapper (FSDP2 `set_requires_gradient_sync`, DDP `require_backward_grad_sync`, no-op single-GPU) so all-reduce fires once per optimizer step. DDP `static_graph=True` is incompatible with mid-run toggling and is detected via the `_bhaskera_static_graph` attribute set in `ddp.py`.
- **Router detection must stay parent-scoped.** Substring-matching `gate`/`router` finds `gate_proj` in every SwiGLU model and wrongly excludes it from LoRA targets. Router search is restricted to modules whose parent is the parent of an experts container.
- **Checkpoints are valid only with the `.complete` sentinel**, written last by rank 0. `maybe_resume` ignores directories without it. To skip a suspect checkpoint, delete the sentinel, not the directory.
- **NCCL env vars belong in `scripts/submit.sh`, not Python** — Ray Train calls `init_process_group` before user code runs, so setting them in-process is too late.

## Conventions

- Extend by adding files, not editing core code — see ARCHITECTURE.md §7 for the add-a-dataset / format / architecture / logger / strategy recipes.
- All modules start with `from __future__ import annotations`; module docstrings explain *why*, and comments frequently reference the design rationale rather than restating code.
- CLIs use stdlib `argparse` and preserve exit codes.
